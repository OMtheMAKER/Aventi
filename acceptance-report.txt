1. WHAT THIS PROJECT IS
--------------------------------------------------------------------------------
Aventi (from the French "Avenir" = Future) is a self-hosted, offline-first
hackathon platform covering the complete event lifecycle: dual-portal auth
with role separation, events with full briefings, deadline-gated registration,
team forming (invite links + open slots), draft→final submissions with a
code-freeze, public gallery, organizer-configurable weighted-rubric judging
with per-judge z-normalization, configurable community voting (open /
email-gated / authenticated, simple or quadratic), and the full stretch tier —
complete REST API, HMAC-signed webhooks, publicly verifiable certificates,
embeddable gallery widget, bulk import/export, plus an event chat lounge with
moderation.

Everything runs from ONE command with zero external services required:
    docker compose up
or, without Docker:
    cd backend && pip install -r requirements.txt
    uvicorn app.main:app --port 8000     →  http://localhost:8000

Highlights of what the suites actually prove:
  • T2.03-style role isolation: a non-assigned judge gets 403 from the BACKEND
    (the UI hiding things is only cosmetic; the API enforces the rule).
  • Weighted rubric validation (2-10 criteria, weights must sum 100) and
    rubric snapshots frozen onto every score row.
  • Per-judge z-normalization driving the leaderboard; CSV exports at every
    stage (registrations, submissions, raw scores, judge progress,
    votes+comments, final results).
  • Voting: configurable access + modes, results hidden during the window,
    stable-per-voter randomized ballot order, Gmail dot-alias normalization,
    rate limits, duplicate-comment detection, organizer audit trail (UI + CSV).
  • Chat: participant/team/announce channels, member-only team walls,
    reactions, rate limits, report→moderation, soft-delete, mute/ban.
  • T4: 8 HMAC-signed webhook event types with delivery log + ping test,
    verifiable certificates (incl. signed judge records), no-login embeddable
    widget, idempotent CSV bulk import with per-row skip reasons, and a
    full-event EVERYTHING.json export.

4. EXTRA ENGINEERING BEYOND THE SPEC
--------------------------------------------------------------------------------
  • Round-wise deliverables: every event round gets its own artifact slot on a
    submission (Round 1: PPT deck, Round 2: prototype video, …) — independent
    save/upload per round, re-saving updates that round, judges see all rounds
    while scoring, and write access locks at the code-freeze.
  • Per-round REQUIREMENTS set by the organizer: each round declares its
    artifact type (any / link only / file only), an accepted-extension list
    (e.g. "ppt,pptx,pdf") and its own deadline — all enforced SERVER-SIDE
    (400 on violation), and surfaced to participants on the event page and on
    their submission board (requirement chips, due dates, "deadline passed"
    lock state, file-type-restricted picker).
  • Judge bench shows every submitted artifact with clickable DOWNLOAD links
    for uploaded files (served via /api/submissions/rounds/files/{id}).
  • Admin "View as Judge" panel: pick any event + judge to see an exact
    READ-ONLY replica of that judge's bench (assignments, rubrics, submitted
    per-round deliverables) via GET /api/judging/preview-queue/{judge_id} —
    organizer-only, payload identical to the judge's own queue.
  • Cinematic MacBookBoot intro on the landing page (desktop only; small
    screens skip straight to the site by design). Pure CSS/DOM — no libraries.
  • Live "right now" event card fed by the real /api/events data.
  • Optional OAuth (Google/Discord/GitHub) wired end-to-end but env-gated:
    set GOOGLE_CLIENT_ID/SECRET (+ PUBLIC_BASE_URL) to switch the demo social
    handshake to the real provider consent flow.
  • Optional SMTP delivery of email-gate voting codes (set SMTP_HOST + creds);
    unset → offline demo shows the code inline, as the spec's offline-first
    rule demands.
  • WebSocket live push for chat (/api/chat/ws/{event_id}) — poke-only design
    (socket carries no message content; clients refetch via authenticated REST,
    so visibility rules live in exactly one place). Polling fallback when the
    socket is unavailable.
  • DATABASE_URL support: SQLite stays the offline default; point it at
    PostgreSQL/MySQL for multi-instance deployments (commented docker-compose
    service included).

5. KNOWN LIMITATIONS (honest, by design or by scope)
--------------------------------------------------------------------------------
  • Real OAuth is account-gated by the provider: a demo deployment cannot
    show Google's consent page until the deployer registers their own OAuth
    client. The dogfood spec is self-hosted/offline — the demo handshake is
    the compliant default; real keys are a deploy-time setting.
  • Real email delivery needs SMTP credentials (env-gated, off by default).
  • Chat polling→WebSocket upgrade is progressive enhancement; both paths are
    covered, but the socket itself is not individually unit-tested.
  • No browser-automation (E2E) suite ships with the repo; every user-facing
    action is covered at the API level instead (the suites above exercise the
    exact endpoints the UI calls).
  • Certificates are optimized for print-to-PDF (one-click button on the cert
    page); there is no server-side PDF renderer (kept dependency-free).
  • Mobile screens intentionally skip the intro animation.
